# データ保持・検索システムの設計方針（一般公開向け）

一般公開にあたり、「全データを分析したいユーザー」「直近の傾向だけ知りたいユーザー」「特定のシーズン（アクト）ごとに振り返りたいユーザー」など、多様なペルソナに対応するためのデータ保持および検索システムの設計方針をまとめます。

## 1. ユーザーペルソナと求められる検索要件

| ペルソナ | ニーズ | 検索・フィルタリング要件 | データ保持の課題 |
| :--- | :--- | :--- | :--- |
| **ライト層** (デイリー利用者) | 直近の調子や、直前の試合の反省を手軽に行いたい | ・直近20〜50試合のサマリ表示<br>・最新試合への即時アクセス | データ量は少ないが、アクセス頻度が高いためAPIリクエスト制限に注意が必要。 |
| **ミドル層** (シーズン/アクト区切り) | 「今スプリットの勝率」「パッチ更新後の影響」など期間を区切って分析したい | ・シーズン（Split）やパッチバージョンでの絞り込み<br>・ランク戦（Solo/Duo, Flex）のみの絞り込み | 指定期間のデータを網羅的にDBに保持しておくか、都度Riot APIをページネーションで遡る必要がある。 |
| **コア層** (生涯戦績・ガチ勢) | 過去全ての対面データ、全メモを蓄積し、自分の財産として分析し続けたい | ・全期間対象の対面検索<br>・「対面チャンピオン」や「自分の使用チャンピオン」でのクロス検索 | 全ユーザーの全試合（生JSON含む）を保存すると、DBのストレージコストが爆発的に増加する。 |

## 2. システム設計の方向性（ハイブリッド・アプローチ）

すべてをRiot APIの都度取得で賄うことはレートリミットの観点で不可能であり、かといって全ユーザーの全データを永続保存するのはコスト面で非現実的です。
したがって、**「ログインユーザー（自分自身）」と「ゲスト検索（他人）」でデータ保持の戦略を分ける** SaaSライクなアプローチを推奨します。

### 2-A. ゲスト検索（他人の戦績検索）の戦略
- **直近データのみ保持**: ゲストによる任意のサモナー検索は、**直近20〜50試合のみ**を Riot API から取得・同期します。
- **揮発性**: 一定期間（例: 1週間）アクセスがない他人のデータは、キャッシュとして扱い、古い生データ（生JSON）から定期バッチで削除（パージ）してストレージを節約します。

### 2-B. ログインユーザー（自分自身の戦績管理）の戦略
- **データの永続化と蓄積**: ユーザー登録（Riot連携など）を行い「自分のアカウント」として登録したサモナーのデータは、**バックグラウンドジョブで定期的にRiot APIをポーリングし、DBに永続的に蓄積（アーカイブ）**します。
- **生JSONの分離（Cold Storage化）**:
  - `matches.raw_info` などの巨大な生JSONは、試合から3ヶ月経過後に Cloud Storage (S3 / GCS 等) に退避、または削除します。
  - 勝敗、KDA、CS、対面チャンプ、反省メモなどの「正規化されたデータ」のみをRDBに残すことで、数千試合蓄積してもDBサイズを数MBに抑えつつ、超高速な検索・集計を実現します。

## 3. GraphQL API と UI の検索インターフェース設計

バックエンド（GraphQL）およびフロントエンドのUIにおいて、ペルソナに応じた柔軟な検索を提供するための仕様案です。

### 3-1. GraphQL クエリ引数の拡張
対面分析（`matchupSummaries`）や試合履歴（`matches`）を取得するクエリに、以下のフィルタ引数（Arguments）を追加します。

```graphql
query GetSummonerAnalysis($puuid: String!, $filter: AnalysisFilterInput) {
  summoner(puuid: $puuid) {
    matchupSummaries(filter: $filter) {
      championName
      opponentName
      winRate
      # ...
    }
  }
}

input AnalysisFilterInput {
  timeframe: TimeframeEnum   # RECENT_20, CURRENT_SPLIT, ALL_TIME など
  queueType: QueueEnum       # RANKED_SOLO_5x5, RANKED_FLEX_SR など
  patchRange: String         # 例: "14.1-14.5" (実装難易度高め、将来拡張)
}
```

### 3-2. フロントエンド UI の検索コントロール
ユーザーが迷わず目的のデータにアクセスできるよう、画面上部に**グローバルフィルター**を配置します。

1. **期間タブ (Timeframe Tabs)**
   - `[ 直近20試合 ]` `[ Split 1 ]` `[ Split 2 ]` `[ 全期間 ]` のようなタブまたはセレクトボックス。
   - ※「全期間」や過去のスプリットは、蓄積データがない場合は「データを同期する（数分かかります）」といったボタンを表示し、非同期でRiot APIから過去分をフェッチするUXにします。
2. **キュー・ロール絞り込み (Queue & Role Filter)**
   - 「ランクソロのみ」「TOPレーンのみ」といった絞り込み。
3. **対面絞り込み (Matchup Search)**
   - 「自分が〇〇を使った時」「相手が〇〇の時」を即座に探せる検索バー（すでにADR-0010のUC-A1で定義されているものを拡張）。

## 4. 優先して取り組むべきタスク (Next Actions)

一般公開に向けた本要件のタスク化です。

- [ ] **GraphQL API への絞り込み (Filter) 引数の実装**: 既存の `matchupSummaries` リゾルバに対して、まずは `limit` (直近N件) と `queue` (ランクのみ等) の引数を追加する。
- [ ] **フロントエンドのフィルターUI実装**: 画面上部に期間やキューを選択できるコントロールコンポーネントを配置し、GraphQLクエリの再フェッチと連動させる。
- [ ] **過去データ同期（オンデマンド・フェッチ）機能の設計**: ユーザーが「過去のデータをもっと見る」を押した際、Riot API のページネーションを用いて過去の試合をバックグラウンドで取得し、WebSocket や Polling で画面を更新する仕組みを作る（Solid Queue / ActionCable の活用）。
- [ ] **ストレージ節約バッチの作成 (Cron)**: 登録ユーザー以外の古い生JSONデータ（`raw_info`）を定期的に NULL に更新または削除し、SQLite/PostgreSQL の肥大化を防ぐ Rake タスクを作成する。
