# [ADR-0011] 試合同期の非同期ジョブ化 (Solid Queue) と本番 PostgreSQL ハイブリッド接続設計

- **ステータス**: Accepted
- **決定日**: 2026-09-06
- **決定者**: チーム / 開発者

---

## コンテキスト（背景・課題）

当プロダクトは「個人専用のソロランクPDCAツール」として、Riot Games APIから直近15試合の詳細データおよびタイムライン（GD@14、アイテム購入履歴）を取得・保存している。

これまで、サモナーの初期登録や「最新データを再取得」を実行した際、**HTTPリクエストの内部で外部APIへのリクエストを直列同期実行**していた。これにより以下の課題が存在していた：

1. **HTTPレスポンスの遅延とタイムアウトリスク**:
   - 15試合分の詳細およびタイムラインを外部APIから取得する際、レートリミット対策のスリープ（`sleep 0.06`）を含めて数秒〜十数秒のレイテンシが発生する。
   - 一般的なクラウドPaaS（Render, Vercel, Railway等）ではリクエストタイムアウト（30秒〜60秒）が設定されており、通信瞬断やリトライが発生した際に504 Gateway Timeoutになるリスクがあった。
2. **UIブロッキングによるUX低下**:
   - データ取得完了まで画面全体がローディングスピナーで塞がれ、過去のメモや対面カードの閲覧が阻害されていた。
3. **本番データベース（PostgreSQL）への適応要件**:
   - 本番環境（Render / Neon / Railway等）で安定稼働させるためには、ローカル用のSQLite3だけでなく、業界標準であるPostgreSQLでの稼働準備が必要である。
   - ただし、開発・テスト環境での手軽さ・高速性を維持するため、ローカルではSQLite3を継続利用できるハイブリッド構成が望ましい。

---

## 決定事項 (Decision)

### 1. Rails 8 標準の `Solid Queue` / ActiveJob による試合同期の非同期化

外部Redisなどの追加インフラを必要とせず、データベースだけで完結するRails 8標準の **`Solid Queue`** を活用し、試合同期処理を完全非同期化する。

1. **`SyncSummonerJob` の新設**:
   - ActiveJobとして実装し、`SummonerSyncService.new.sync_summoner` をバックグラウンドで実行。
2. **状態管理カラムの追加 (`summoners` テーブル)**:
   - `sync_status`: `"idle"`（待機中）, `"syncing"`（同期中）, `"failed"`（同期失敗）
   - `sync_error`: エラー発生時のメッセージ
3. **GraphQL APIの非同期連携**:
   - `syncMySummoner(force: Boolean)` Mutationを新設。ジョブを即座にキューへ積み、現在のステータスを数ミリ秒で返却。
   - `SummonerType` に `sync_status` および `sync_error` を公開。
4. **フロントエンドのノンブロッキングUX**:
   - 同期実行中（`syncStatus === "syncing"`）もユーザーは既存の戦績・対面メモを自由に閲覧可能。
   - ヘッダーやプロフィール上に「戦績を非同期同期中...」のスピナーを表示し、3秒間隔でポーリングして完了時に自動で画面を最新化。

---

### 2. PostgreSQL 本番接続対応（マルチDBハイブリッド設計）

1. **`pg` gem の導入**:
   - `backend/Gemfile` に `gem "pg", "~> 1.1"` を追加。
2. **`config/database.yml` のハイブリッド環境変数対応**:
   - `production` 設定において、環境変数 `DATABASE_URL` が渡されている場合は PostgreSQL アダプター（接続プール付き）を使用。
   - `DATABASE_URL` が未指定の場合はローカル SQLite3（`storage/production.sqlite3`）にフォールバック。
   - 開発（`development`）・テスト（`test`）環境は引き続き軽量な SQLite3 をそのまま使用し、ローカル開発の俊敏性を維持。

## 結果・影響 (Consequences)

### メリット
- **タイムアウトの完全解消**: HTTPリクエストはジョブのエンキューのみで数ミリ秒で完了するため、Gateway Timeoutを回避できる。
- **UXの劇的向上**: 同期中であってもユーザーの画面操作がブロックされず、快適にPDCAを回せる。
- **本番インフラの柔軟性**: Render、Railway、Neon等のPostgreSQL環境へ追加コード修正なしでデプロイ可能。
- **追加インフラコストゼロ**: Solid QueueはDB相乗りで動作するため、Redis等の別サーバー代がかからず0円運用に適している。

### 留意点
- フロントエンド側で同期完了を検知するためのポーリング処理（3秒間隔）が必要となる。
