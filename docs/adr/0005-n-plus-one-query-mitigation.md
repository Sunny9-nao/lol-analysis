# [ADR-0005] GraphQLにおけるN+1クエリ対策方針

- **ステータス**: Accepted
- **決定日**: 2026-09-05
- **決定者**: 開発者

## コンテキスト（背景・課題）
GraphQL はクライアントが必要なフィールドを自由にネストして要求できるため、関連テーブル（`match_participants` ➔ `match` や `match_note`）を取得する際に、レコード数 $N$ に応じて $N$ 回の SQL が発行される「N+1問題」が原理的に発生しやすい。
試合履歴が増加した際にデータベース負荷が急増しレスポンス性能が低下するのを防ぐため、N+1対策を標準化する必要がある。

## 検討した選択肢
1. **選択肢A (ActiveRecordの `includes` / `preload` 先読み)**:
   - クエリのルートやリレーション定義で事前に `includes(:match, :match_note)` を実行。
   - メリット: 実装がシンプルでRailsエンジニアにとって馴染みが深い。
   - デメリット: クライアントがそのフィールドを要求しなかった場合でも先読みが発生する。
2. **選択肢B (GraphQL::Dataloader による遅延バッチロード)**:
   - `graphql-ruby` 組み込みの Dataloader を利用し、実際にフィールドが要求された時だけIDを集約して `WHERE id IN (...)` で一括取得。
   - メリット: クライアントが要求した時のみ実行され、Over-fetching が発生しない。
3. **ハイブリッド方針** 【採用】:
   - 密結合している主リレーション（参加レコードに対する親の `match` やメモ `match_note`）は、取得スコープで安全に `includes` を適用。
   - 疎結合なリレーションや将来の外部データ取得には `GraphQL::Dataloader` を活用する。

## 決定事項 (Decision)
1. サモナーの参加試合レコード一覧を取得する際、デフォルトで `includes(:match, :match_note)` を適用し、SQL発行回数を最小化する。
2. RSpec にクエリ実行回数を監視するテスト（N+1検知テスト）を導入し、リグレッションを自動防止する。

## 結果と影響 (Consequences)
### ポジティブな影響（メリット）
- 取得する試合数が1件でも100件でも、SQL発行回数が一定（3〜4回程度）に抑えられ、性能が大幅に向上する。
- 自動テストでクエリ数が担保されるため、将来の機能追加時もN+1の再発を即座に検知できる。

### ネガティブな影響 / トレードオフ
- クライアントが `match` の情報を要求しない場合でも先読みのオーバーヘッドがわずかに発生するが、ローカルSQLite/少件数の環境では無視できる。
