# [ADR-0004] TDD (テスト駆動開発) とテスト戦略の策定

- **ステータス**: Accepted
- **決定日**: 2026-09-05
- **決定者**: 開発者

## コンテキスト（背景・課題）
機能開発を迅速かつ安全に進め、品質を継続的に担保するため、TDD（Test-Driven Development: テスト駆動開発）を開発標準として導入する。
特に GraphQL API と外部REST API（Riot API）を組み合わせたアーキテクチャでは、以下の課題がある：
1. テスト実行時に本物の外部APIを叩くと、APIレート制限超過や通信遅延、ネットワーク不安定性によるテストのFlaky化（不安定化）が発生する。
2. GraphQL はクライアントからの自由なクエリ要求に応じるため、コントローラー単体ではなく、スキーマ全体を通した統合テスト（Request Spec）が最も壊れにくく信頼性が高い。

## 検討した選択肢

### 1. テストフレームワーク
- **選択肢A (Minitest)**: Rails標準。シンプルだが、マッチャーや表現力、コミュニティ資産において実務でのRSpecの優位性が高い。
- **選択肢B (RSpec)** 【採用】: `describe` / `context` / `it` によるBDD（振る舞い駆動開発）構文が明確で、テストケースの整理が容易。

### 2. テストデータ管理
- **選択肢A (Fixtures)**: YAMLで固定データを管理。リレーションが増えると保守が困難。
- **選択肢B (FactoryBot)** 【採用】: コードベースで柔軟にモデルインスタンスを生成でき、ActiveRecordとの親和性が高い。

### 3. 外部APIモック方針
- **選択肢A (VCR)**: 初回通信をカセットとして録画。APIの変更に強いが、APIキー管理が必要。
- **選択肢B (WebMock)** 【採用】: HTTPリクエストを明示的にスタブし、外部通信を完全に遮断。テストがミリ秒単位で高速実行可能。

## 決定事項 (Decision)

以下のツール群とテストピラミッドを採用する：

1. **採用ライブラリ**:
   - `rspec-rails`
   - `factory_bot_rails`
   - `webmock`

2. **テストピラミッド方針**:
   - **GraphQL Request Spec（最重視）**: `post "/graphql"` に実際のクエリ文字列を送り、レスポンスの JSON 構造（`data`, `errors`）を検証する。GraphQL の振る舞い保証の主軸とする。
   - **Model Spec**: バリデーション、アソシエーション、ドメイン計算ロジック（`kda_ratio` 等）をテストする。
   - **Service Spec**: WebMock を使い、HTTPステータス（200, 403, 404, 429）ごとの例外発生とデータパースをテストする。

3. **TDDの進め方**:
   - 新規機能追加（特に Mutation や複雑な Query）時は、必ず先に Request Spec を書き、失敗を確認（Red）してから最小限の実装を行い（Green）、その後コードを整える（Refactor）。

## 結果と影響 (Consequences)

### ポジティブな影響（メリット）
- テスト実行が完全オフラインで高速に行える（外部APIの制限を消費しない）。
- リファクタリングやGraphQLスキーマの変更によるリグレッション（意図しない破壊）を即座に検知できる。
- 仕様がテストコードとしてそのままドキュメント化される。

### ネガティブな影響 / トレードオフ
- テストコードの記述工数がかかる。ただし、将来のデバッグや保守コストを大幅に削減できる。
