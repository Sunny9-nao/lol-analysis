# [ADR-0001] プロジェクト構成と初期技術スタックの選定

- **ステータス**: Accepted
- **決定日**: 2026-09-05
- **決定者**: 開発者

## コンテキスト（背景・課題）
Rails を用いたバックエンド開発および GraphQL の構文・レイヤリング（どの層にどのようなコードを書けば動くか）の実装力向上を目的とする。
題材として、League of Legends（LoL）の戦績分析アプリ（BFF: Backend For Frontend パターン）を扱う。
既存の `lol-app`（Next.js）とは完全に切り離し、将来的なフロントエンド開発も見据えた構成を初期設計する必要がある。

## 検討した選択肢

### 1. プロジェクトリポジトリ構成
- **選択肢A (完全分離リポジトリ)**: `lol-backend`, `lol-frontend` を完全に別リポジトリとする。
- **選択肢B (モノレポ構成・ディレクトリ分離)**: `lol-analysis/` 直下に `backend/`, `frontend/`, `docs/` を集約する。

### 2. データベース選定
- **選択肢A (PostgreSQL)**: 実務で最も広く使われている RDBMS。Docker やローカルサービスの管理が必要。
- **選択肢B (SQLite)**: Rails 8 標準。ファイルベースで外部サーバー不要、初期セットアップが極めて容易。

### 3. API設計方針
- **選択肢A (REST API)**: Rails標準のScaffold/コントローラー中心。
- **選択肢B (GraphQL API)**: `graphql-ruby` を導入。クライアント主導のデータ要求、BFFでの集約、型システムを活用。

### 4. 認証・認可方針
- **選択肢A (Devise / JWTによる本格認証)**: ログイン・セッション管理を構築。
- **選択肢B (認証レス + 公開/非公開ステータスハンドリング)**: 一般的な戦績検索サイト同様にゲスト利用を前提とし、プレイヤーの「公開/非公開」状態をGraphQLの型・エラーでハンドリングする。

## 決定事項 (Decision)

1. **ディレクトリ構成**:
   - `lol-analysis` 配下に `backend/`, `frontend/`, `docs/adr/` を配備するモノレポ構成（選択肢B）を採用。ドキュメントとコードの整合性を担保しやすくする。
2. **データベース**:
   - **SQLite**（選択肢B）を採用。環境構築の摩擦を最小化し、ActiveRecord + GraphQL の連携練習に即座に注力できる環境とする。
3. **API方式**:
   - **GraphQL (`graphql-ruby`)**（選択肢B）を採用。Riot APIの複数エンドポイントをRails側で束ね、単一のGraphQLエンドポイントとしてクライアントに提供するBFF構成とする。
4. **認証認可**:
   - 初期段階では**認証レス**（選択肢B）を採用。アカウントの「公開/非公開」ステータスハンドリングを GraphQL の Resolver/Type で表現することに特化する。

## 結果と影響 (Consequences)

### ポジティブな影響（メリット）
- 余計な認証機能やDBセットアップに時間を取られず、GraphQL特有のレイヤリング（Types, Queries, Mutations, Resolvers, Error Handling）の習得に集中できる。
- `docs/adr/` により、今後の設計変更や議論を客観的にトラッキングできる。
- 将来フロントエンド（React/Vite/Apollo）を追加した際も、同一リポジトリ内で GraphQL Code Generator による型連携がスムーズに行える。

### ネガティブな影響 / トレードオフ
- SQLite では本番環境での大規模並行書き込みに制限があるが、ローカル学習フェーズでは問題にならない。必要に応じて PostgreSQL への移行も容易（ActiveRecordを介しているため）。
- 認証システム（JWTやDevise）の構築経験は別タスクで扱う必要がある。
