バックエンドの設計方針と特徴

このバックエンドは、「Riot Games APIからの大量の生データ取得」と「ユーザー自身の振り返りメモ・相性分析」を分離・最適化して結びつけるように設計されています。

  • 生JSON保持 ＋ 正規化カラムのハイブリッド: 将来の仕様変更や詳細表示用に生JSON（raw_info, raw_participant）を保持しつつ、分析で多用するGD@14やCS、勝敗は検索用カラムに展開。
  • GraphQL BFF: フロントエンドに必要な粒度（対面サマリ、カウンター逆引き、時系列グラフ）を1クエリで提供。
  • 堅牢な同期パイプライン: Riot APIのレート制限（秒間/2分間）に対応するリトライ・ジッター制御と、Solid Queueによる非同期バックグラウンド処理。

推奨する読み進めの順序

  1. 設計意図 & データモデル（土台を固める）
  2. APIクライアント & 同期処理（外部データ流入）
  3. タイムライン解析ロジック（競技特化のインサイト）
  4. 対面集計サービス（コア機能のビジネスロジック）
  5. GraphQL スキーマ & リゾルバ（クライアント公開境界）
  6. 非同期ジョブ & ゾンビ自己修復（運用の堅牢化）

タイムライン解析ロジック（試合展開のインサイト化）
TimelineAnalysisService
独自アルゴリズム

試合終了時の結果だけでなく、「レーン戦で勝っていたのか負けていたのか」を客観的に評価するための時系列解析エンジンです。

対象ファイル 重要度 注目ポイント・着眼点
backend/app/services/timeline_analysis_service.rb 最重要 analyze メソッドの全体像：
  • calculate_diffs: 14分時点（プレート脱落・レーン戦終了の目安）のフレームを抽出し、ゴールド差 (GD@14) とCS差 (CSD@14) を算出。±500G または ±20CS を閾値として lane_outcome（win / loss / even）を判定。
  • extract_items: ITEM_PURCHASED イベントと ITEM_UNDO イベントを走査し、時系列でのアイテム購入履歴を構築。
  • extract_kill_events: 誰が誰を倒したかのキルログから「対面ソロキル」「対面被キル」「通常キル」「デス」を分類。
💡 読む時のポイント:
  • Riot APIのTimelineデータ構造（info.frames[n].participantFrames と events）がどのようにRubyのHashから集約・整形されているかを追ってみてください。

全体アーキテクチャ概要

クライアント（Next.js）からの単一エンドポイント POST /graphql に対して、Railsバックエンドが認証・サービス・DB・非同期キュー・外部APIを統合して処理します。

データエンティティの関係性 (ER構造)

Summoner

LoLプレイヤーアカウント

  • puuid (一意な識別子)
  • game_name / tag_line
  • sync_status (idle/syncing/failed)
  • 1 : N match_participants
  • 1 : 1 user (任意)
MatchParticipant (要)

特定プレイヤーの1試合の戦績記録

  • champion_name / opponent_champion_name
  • win, kills, deaths, assists, cs
  • gold_diff_at_14, cs_diff_at_14, lane_outcome
  • early_items, gold_timeline, kill_events (JSON)
  • N : 1 summoner, N : 1 match
Match

試合全体のデータ（全プレイヤー共通）

  • match_id (例: JP1_123456)
  • queue_id (420: Ranked Solo/Duo)
  • game_duration, game_creation
  • raw_info (10人分の生データJSON)
  • 1 : N match_participants
MatchNote & User

反省メモとログインユーザー

  • content (反省テキスト)
  • matchup_tag (Hard / Even / Easy)
  • N : 1 user, N : 1 match_participant
  • ※ユーザー本人の試合にのみ保存を認可

ユースケース 1: Riot ID検索と初回データ同期

ユーザーが「Sunny9#hono」で検索した際、GraphQLクエリから外部APIを呼び出し、DBへキャッシュして返すまでの流れです。

1
GraphQL クエリ受信
Types::QueryType#search_summoner(game_name: "Sunny9", tag_line: "hono")

SummonerSyncService.new.sync が呼び出されます。DBに1時間以内のレコードがあれば外部APIを呼ばず即座に返します。

2
Riot APIからアカウント & サモナー情報取得
RiotApiClient#fetch_account_by_riot_id / #fetch_summoner_by_puuid

タグラインから地域（JP/KR/NA）を自動推定し、PUUID・サモナーレベル・アイコンIDを取得して Summoner レコードを Upsert します。

3
ソロランク試合の取得 & タイムライン解析
SummonerSyncService#sync_match & TimelineAnalysisService#analyze

最新30件の試合ID（queue=420）を取得。未保存の試合について、試合詳細とタイムラインJSONを取得し、14分時点の差（GD@14, CSD@14）やレーン結果を計算して Match と MatchParticipant に保存します。

4
レスポンス返却
Types::Objects::SummonerType

フロントエンドへサモナー情報と直近試合リスト、勝率がGraphQLレスポンスとして返却されます。

ユースケース 2: 対面分析（マッチアップ集計）の表示

特定のチャンピオンを選択した際に、天敵（Hard）や得意な相手（Easy）の戦績を算出する流れです。

1
GraphQL フィールド解決
Types::Objects::SummonerType#matchup_summaries(champion_name: "Ahri")

MatchupAnalysisService.new(summoner: object, current_user: context[:current_user]).summaries_for が呼ばれます。

2
SQLによる対象試合の抽出（ランク戦のみ）
match_participants.joins(:match).where(matches: { queue_id: 420 }, champion_name: "Ahri")

includes(:match, :match_notes) でN+1問題を回避しながら、対面チャンピオン名ごとにグループ化します。

3
スタッツ & メモタグの集計
MatchupAnalysisService#calculate_stats_for_group

勝率、平均KDA、CS/分を算出。さらに現在ログイン中のユーザーが記録したメモから「Hard/Even/Easy」タグの件数と最新メモを紐づけてソートします。

ユースケース 3: 試合の振り返りメモ保存

ユーザーが試合詳細モーダルで「反省点」や「相性タグ」を入力して保存する流れです。

1
Mutation 実行 & 認可チェック
Mutations::SaveMatchNote#resolve(match_participant_id, content, matchup_tag)

ログイン中か検証し、さらに participant.summoner_id == current_user.summoner_id であることをチェック（他人の試合メモの改ざんを防止）。

2
レコード保存 (Upsert)
MatchNote.find_or_initialize_by(user_id: ..., match_participant_id: ...)

1ユーザー×1試合参加レコードに対してメモが1つだけ存在するように保存・更新します。
