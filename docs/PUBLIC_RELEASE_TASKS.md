# 一般公開（Public Release）に向けたタスクリスト

本プロジェクト（League of Legends 戦績分析アプリ）をローカル学習・プロトタイプ段階から、一般ユーザーへ公開するプロダクトレベルへ引き上げるために必要な要件とタスクをまとめます。

## 1. 機能要件 (Functional Requirements)

### 1.1. Riot API の本番対応
- [ ] **プロダクションキーの取得**: 個人用（Personal API Key）から、Riot Games にプロダクト申請を行い、プロダクションキー（Production Key）を取得する。
- [ ] **レートリミット（429 Too Many Requests）対策**: Riot APIの制限に到達した際のリトライロジック（Exponential Backoff）や、ユーザーへの親切なエラー表示を実装する。
- [ ] **API障害時のフォールバック**: Riot API側がダウンしている際に、アプリ全体がクラッシュしないよう適切なエラーバウンダリを設定する。

### 1.2. ユーザー認証とデータ保護（※最重要）
- [ ] **メモ編集権限の保護**: 現在の「誰でもRiot IDを入力すれば閲覧・編集できる（認証レス）」仕様のまま公開すると、他人の反省メモを勝手に書き換えられるリスクがあります。
  - **対応案A**: Riot アカウントによる OAuth 認証（Riot Sign In）の導入（推奨）。
  - **対応案B**: アカウント登録制（メール＋パスワード or Google/Discordログイン）とし、Riot IDを連携させる。
  - **対応案C**: 完全に認証レスを貫く場合、メモデータはサーバーではなくブラウザの `localStorage` 等に保存する形に変更する。

### 1.3. 法的要件・コンプライアンス
- [ ] **利用規約 (Terms of Service) の作成**: サービスの免責事項などを明記する。
- [ ] **プライバシーポリシーの作成**: ユーザーのRiot IDやメモデータをどのように扱い、保存するかを明記する。
- [ ] **Riot Games Legal Jibber Jabber の掲示**: Riot APIの利用規約に従い、フッター等に「This product isn't endorsed by Riot Games...」の指定文言を必ず記載する。

### 1.4. SEO・シェア機能 (OGP)
- [ ] **OGP（Open Graph Protocol）の設定**: X (Twitter) や Discord で URL を共有した際に、サービス名やアイキャッチ画像が綺麗に表示されるようにメタタグを設定する。
- [ ] **動的メタデータ**: サモナーのページをシェアした際に、「[サモナー名]の戦績分析」のように動的なタイトルが出るように Next.js 側で調整する。

## 2. 非機能要件 (Non-Functional Requirements)

### 2.1. セキュリティ (Security)
- [ ] **CORS の厳格化**: Rails バックエンドの API エンドポイントへのアクセスを、許可されたフロントエンドのドメイン（例: `https://lol-analysis.example.com`）のみに制限する。
- [ ] **GraphQL Introspection の無効化**: 本番環境ではスキーマ情報を外部から読み取られないよう、Introspection をオフにする。
- [ ] **シークレット管理**: Riot API キーやデータベースのパスワードを `.env` に直書きせず、ホスティングサービスの Secret Manager などを使用して安全に管理する。
- [ ] **自社 API のレートリミット**: `Rack::Attack` 等を導入し、悪意のあるユーザーによる GraphQL エンドポイントへの大量リクエスト（DoS攻撃）を防ぐ。

### 2.2. パフォーマンス (Performance)
- [ ] **API レレスポンスのキャッシュ**: Riot API から取得した変更の少ないマスターデータ（チャンピオン情報、アイテム情報など）を Redis 等でキャッシュする。
- [ ] **N+1 クエリの根絶**: GraphQL の Resolver 内で N+1 が発生していないか確認し、必要に応じて `graphql-batch` (Dataloader パターン) を適用する。
- [ ] **アセットの最適化**: Next.js の `next/image` を活用し、チャンピオンやアイテムの画像を適切に圧縮・キャッシュして配信する。

### 2.3. 監視と分析 (Observability)
- [ ] **エラートラッキングの導入**: Sentry 等を導入し、フロントエンド・バックエンドで発生した例外エラーを検知・通知する仕組みを作る。
- [ ] **アクセス解析の導入**: Google Analytics 4 (GA4) または Vercel Web Analytics などを導入し、ユーザーの利用状況を計測する。

## 3. インフラ整備 (Infrastructure)

### 3.1. データベースの移行
- [ ] **PostgreSQL への移行**: 現在の SQLite はローカル開発・学習用としては優れていますが、本番環境での並行アクセスやバックアップ運用を考慮すると、PostgreSQL 等の堅牢な RDBMS への移行を強く推奨します。
- [ ] **定期バックアップ設定**: ユーザーの「反省メモ」という資産が消えないよう、DBの自動バックアップ運用を確立する。

### 3.2. ホスティング・デプロイ環境
- [ ] **フロントエンド (Next.js)**: Vercel または Cloudflare Pages での本番環境構築。
- [ ] **バックエンド (Rails API)**: Render, Fly.io, または Google Cloud Run でのコンテナデプロイ環境構築。
- [ ] **プロダクション向け Dockerfile の作成**: バックエンド用の軽量で安全な（非 root ユーザー実行など）本番用 Docker イメージを作成する。
- [ ] **独自ドメインと SSL の設定**: カスタムドメインを取得し、HTTPS 通信を強制する。

### 3.3. CI/CD (継続的インテグレーション・デリバリー)
- [ ] **自動テストの組み込み**: GitHub Actions 等を設定し、PR 作成時に RSpec (バックエンド) や Jest/Vitest (フロントエンド) が自動実行されるようにする。
- [ ] **Lint/Format の自動チェック**: Rubocop, ESLint, Prettier によるコード規約チェックを CI 上で実行する。
- [ ] **自動デプロイ**: `main` ブランチへのマージをトリガーに、ステージング・本番環境へ自動デプロイされるパイプラインを構築する。
